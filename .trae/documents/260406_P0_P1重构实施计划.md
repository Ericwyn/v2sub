# v2sub P0 / P1 重构实施计划

基于现有重构策略文档 [260406_多阶段重构.md](file:///d:/Chaos/go/v2sub/docs/260406_多阶段重构.md) 与当前代码实现，下面给出可直接落地的 P0、P1 任务规划。

---

## 1. 现状结论

当前关键问题已在代码中确认：

- `-conn start` 在 [conn_mgr.go](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L58-L99) 中通过 `command.RunSync(...)` 同步阻塞执行 `v2ray`
- `-conn kill` 在 [conn_mgr.go](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L135-L164) 中依赖 `ps + grep + kill`
- Web 在 [service.go](file:///d:/Chaos/go/v2sub/web/service.go#L12-L41) 中通过再次执行 `v2sub -conn start/kill` 控制连接
- Web `status` 在 [api.go](file:///d:/Chaos/go/v2sub/web/api.go#L79-L88) 中仅返回 `runFlag` / `lastStartTimeUnix`
- `utils/command` 当前能力集中在命令执行，缺少稳定的进程管理抽象，见 [run.go](file:///d:/Chaos/go/v2sub/utils/command/run.go)

因此，P0 先解决“进程可管、状态真实”；P1 再解决“CLI/Web 共用同一套 runtime service”。

---

## 2. 总体策略

### P0 目标

在尽量不大拆结构的前提下，把 `conn` 从“阻塞启动器 + 模糊 kill”改成“可追踪运行入口”。

P0 完成后应满足：

- `v2sub -conn start` 后立即返回，不再阻塞 CLI
- 运行中的 `v2ray` 有 pid 文件与 runtime 文件
- `v2sub -conn status` 可返回真实状态
- `v2sub -conn kill` 优先按 pid 文件停止
- Web `status` 改为真实查询，不再依赖 `runFlag` 作为主状态源
- 老的 `ps + grep + kill` 逻辑不再承担主路径

### P1 目标

抽出独立 runtime service，让 CLI 与 Web 共用同一套启动/停止/状态逻辑。

P1 完成后应满足：

- `conn` 只做命令参数分发
- Web 不再执行 `v2sub` 二进制控制连接
- start/stop/restart/status 都走内部 service
- 统一状态结构、日志语义、错误返回

---

## 3. P0 实施方案

## 3.1 P0 设计原则

1. 只做必要拆分，不一次性引入大范围 package 重构
2. 优先保证 Linux 运行路径稳定
3. 不先动订阅、节点、配置生成逻辑
4. 对外 CLI 形式尽量保持兼容
5. 为 P1 提前预留接口与状态结构

---

## 3.2 P0 任务拆分

### P0-1 新增运行时元信息定义

建议先在 `conn` 内新增一组运行时结构与常量，先不强制新建 `runtime/` 包。

建议新增内容：

- `type V2rayStatus struct`
- pid 文件路径常量
- runtime 状态文件路径常量
- 运行模式字段

建议状态结构至少包含：

```go
type V2rayStatus struct {
    Running       bool   `json:"running"`
    Pid           int    `json:"pid"`
    StartedAtUnix int64  `json:"startedAtUnix"`
    BinaryPath    string `json:"binaryPath"`
    ConfigPath    string `json:"configPath"`
    Mode          string `json:"mode"`
    Message       string `json:"message"`
}
```

建议路径：

- `/etc/v2sub/v2ray.pid`
- `/etc/v2sub/runtime.json`

原因：当前项目整体配置路径已围绕 `/etc/v2sub/`，P0 优先复用现有目录，避免引入额外目录权限与部署变更。

### P0-2 在 `conn` 内补齐运行时文件读写

新增能力：

- 写 pid 文件
- 读 pid 文件
- 删除 pid 文件
- 写 runtime.json
- 读 runtime.json
- 删除 runtime.json
- stale pid 清理

细化要求：

1. 读 pid 失败时返回明确错误，不 panic
2. pid 文件内容需做整数校验
3. runtime 文件读失败时允许降级，只要 pid 还在就能判断运行中
4. status 查询时，如果发现 pid 不存活，要自动清理 stale pid 与 runtime 文件

### P0-3 增加基础进程管理能力

优先在 [utils/command/run.go](file:///d:/Chaos/go/v2sub/utils/command/run.go) 扩充非 shell 风格能力，而不是继续拼字符串。

建议新增函数：

```go
func StartBackground(name string, arg ...string) (*exec.Cmd, error)
func IsProcessAlive(pid int) bool
func TerminateProcess(pid int) error
func KillProcess(pid int) error
func FindProcess(pid int) (*os.Process, error)
```

实现建议：

- `StartBackground` 使用 `exec.Command` + `Start()`
- 标准输出/错误输出重定向到文件或 `os.DevNull`
- P0 不做完整日志采集，只保证可启动可管理
- `IsProcessAlive` 用 `os.FindProcess` + `Signal(0)` 或 Linux 下等价检查
- `TerminateProcess` 优先发 `SIGTERM`
- `KillProcess` 发 `SIGKILL`

注意点：

- `RunResult("/bin/bash -c")` 保留，P0 不强行清理其他模块依赖
- 新增进程函数尽量独立，避免影响已有 `sub/server` 逻辑

### P0-4 重构 `startV2ray()` 为后台启动流程

改造 [startV2ray](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L58-L99) 的执行语义。

目标流程：

1. 检查 v2ray binary 是否存在
2. 检查当前默认节点是否存在，避免空索引风险
3. 刷新并生成最新 v2ray config
4. 查询当前状态：若旧 pid 存活，则返回“已在运行”或执行显式重启策略
5. 组装 v2ray 启动命令
6. 后台启动进程
7. 将 pid 写入 pid 文件
8. 将运行信息写入 runtime.json
9. 向 CLI 输出结构化启动结果并立即返回

P0 推荐行为：

- 如果已有存活实例，`start` 直接报“already running”，不自动覆盖
- `restart` 留到 P0 后半段或 P1 明确实现

原因：

- 行为更可预期
- 降低“误杀正在运行实例”的风险

### P0-5 新增真实状态查询能力

在 `conn` 增加：

- `Status() V2rayStatus`
- `PrintStatus()`

CLI 增加子命令：

- `v2sub -conn status`

状态查询流程：

1. 读取 pid 文件
2. 判断 pid 是否存活
3. 若存活，尽量合并 runtime.json 返回
4. 若不存在或已失效，则清理 pid/runtime 文件并返回 `Running=false`

CLI 输出建议：

- 保留简单文本输出，兼容现有终端风格
- 同时内部统一返回结构化 status，供 P1 Web 直接复用

### P0-6 重构 `KillV2Sub()` 为按 pid 停止

目标是让 [KillV2Sub](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L135-L164) 从“进程扫描器”改为“受控停止器”。

推荐流程：

1. 读取 pid 文件
2. 若无 pid 文件，直接返回“not running”
3. 若 pid 不存活，清理 stale pid/runtime 文件后返回
4. 优先发送 `SIGTERM`
5. 轮询短时间确认退出
6. 若未退出，再 `SIGKILL`
7. 清理 pid 文件与 runtime 文件
8. 返回最终结果

兼容性建议：

- P0 可保留一个兜底开关：当 pid 文件缺失但用户明确想清理旧环境时，是否允许 fallback 到旧扫描逻辑
- 但默认主路径不要再使用 `ps + grep + kill`

我建议：

- 先不保留 fallback
- 彻底切换到 pid 管理

理由：

- 旧逻辑存在误杀风险
- P0 的目标就是建立新的单一真相来源

### P0-7 调整 `conn.ParseArgs()`

改造 [ParseArgs](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L32-L48)：

新增或调整子命令：

- `start`
- `kill`
- `status`
- `restart`
- `start-pac`

建议语义：

- `start`: 后台启动 v2ray
- `kill`: 停止当前 pid 对应 v2ray
- `status`: 真实查询
- `restart`: `Stop()` 后 `Start()`
- `start-pac`: P0 先保留旧入口，但内部不要再影响主状态逻辑

同时修正文案问题：

当前 `start` 分支执行后打印“v2ray 已停止”，见 [conn_mgr.go](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L36-L39)，这需要修正。

### P0-8 Web `status` 切换到真实状态

P0 先做最小收益改造，不要求 Web 完全去二进制依赖。

优先修改：

- [apiConnStatus](file:///d:/Chaos/go/v2sub/web/api.go#L79-L88)

方案：

- 直接调用 `conn.Status()`
- 返回真实 `running/pid/startedAtUnix/configPath/binaryPath/message`

这样即使 Web 的 start/stop 仍然通过二进制调用，至少 `status` 已能反映系统真相。

### P0-9 Web start/stop 内存状态降级为辅助字段

P0 不一定一次删光 `runFlag` 与 `lastStartTimeUnix`，但要调整职责：

- 不再把它们作为 API 主状态源
- 仅用于 Web 页面上的“请求已发起”类辅助提示
- 最终返回状态应以 `conn.Status()` 为准

如果改动量可控，P0 末尾可直接移除：

- `runFlag`
- `lastStartTimeUnix`

但这不是 P0 的硬性前置条件。

### P0-10 P0 验证任务

必须验证以下场景：

1. `-conn start` 后命令立即返回
2. `-conn status` 显示 running=true 且 pid 正确
3. `-conn kill` 能正常停止该 pid
4. 重复 `start` 时可得到可预期提示
5. 删除进程后 `status` 可清理 stale pid
6. Web `/conn/status` 返回真实状态
7. `start-pac` 不影响新的 pid/status 主流程

## 3.3 P0 推荐改造顺序

建议按下面顺序实施：

1. 在 `utils/command` 增加进程控制函数
2. 在 `conn` 增加 pid/runtime 结构与文件读写
3. 先完成 `Status()`
4. 再改 `startV2ray()` 为后台启动
5. 再改 `KillV2Sub()` 为按 pid 停止
6. 再补 `restart`
7. 最后改 Web `apiConnStatus`
8. 回归测试 CLI 与 Web 基本链路

原因：

- 先有状态，后有启动/停止，调试更顺手
- 可以减少 start/kill 同时改造带来的定位成本

## 3.4 P0 风险与处理

### 风险 1：后台启动后日志缺失

现状里 `start` 的输出直接打印到终端；后台化后默认会丢失。

P0 处理：

- 不强求完整日志系统
- 可先重定向到 `/etc/v2sub/v2ray.log` 或忽略输出
- 把“日志整合”留到 P1 或后续

### 风险 2：`start-pac` 行为混杂

`start-pac` 目前绑定 PAC 服务与 v2ray 启动。

P0 处理：

- 先保持兼容
- 仅保证 PAC 路径不破坏新的主流程
- 不在 P0 做 PAC 架构拆分

### 风险 3：老环境无 pid 文件

用户可能已有手工启动的 v2ray。

P0 处理：

- 新逻辑只管理由 `v2sub` 新启动并记录 pid 的实例
- 不再承诺接管“未知来源”进程

### 风险 4：CLI 函数仍使用 `os.Exit`

当前 [conn_mgr.go](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L50-L56) 与 [conn_mgr.go](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go#L94-L98) 中有 `os.Exit`。

P0 处理：

- 可先维持 CLI 风格
- 但新增内部能力尽量返回 `error`，为 P1 service 化铺路

## 4. P1 实施方案

## 4.1 P1 目标架构

P1 开始正式引入独立运行时层。

建议新增目录：

```text
runtime/
  service.go
  process.go
  state.go
```

推荐职责：

- `runtime/state.go`
  - `V2rayStatus`
  - pid/runtime 文件读写
  - stale state 清理
- `runtime/process.go`
  - 启动、停止、探活等底层过程
- `runtime/service.go`
  - `Start/Stop/Restart/Status`
  - 配置刷新与业务编排

---

## 4.2 P1 核心接口设计

建议定义：

```go
type Service interface {
    Start() (*V2rayStatus, error)
    Stop() (*V2rayStatus, error)
    Restart() (*V2rayStatus, error)
    Status() (*V2rayStatus, error)
}
```

建议默认实现：

```go
type V2rayService struct {}
```

内部编排职责：

- 校验 binary
- 校验当前 server 配置
- 生成 config
- 管理进程生命周期
- 输出统一状态结构

这里要注意：

- `runtime` 负责“运行控制”
- `conf` 继续负责“配置生成”
- `server/sub` 不进入 runtime

---

## 4.3 P1 任务拆分

### P1-1 从 `conn` 抽出状态模型与运行时文件逻辑到 `runtime`

把 P0 里新增在 `conn` 的内容迁移到 `runtime/state.go`：

- `V2rayStatus`
- pid/runtime 路径常量
- 读写函数
- stale 清理函数

完成后 `conn` 不再直接碰状态文件细节。

### P1-2 从 `utils/command` 与 `conn` 抽出进程控制到 `runtime/process.go`

这里不要求完全移除 `utils/command`，但建议让 runtime 层拥有自己清晰的进程语义。

职责包括：

- 构造命令参数
- 后台启动
- 信号终止
- 轮询等待退出
- 强制 kill
- 探活

这样可以避免 `conn` 继续持有大量 OS 细节。

### P1-3 在 `runtime/service.go` 实现统一业务入口

把如下编排从 `conn` 中挪出：

- 选择当前默认节点
- 刷新 config
- 判断 v2ray 新旧命令格式
- 启动 v2ray
- 停止 v2ray
- 查询真实状态

结果：

- `conn` 只负责参数转发
- Web 直接依赖 `runtime`

### P1-4 重构 `conn.ParseArgs()` 为纯 CLI 分发层

目标形态：

- 解析子命令
- 调用 `runtime.Service`
- 打印结果
- 不再自己维护启动/停止细节

`conn` 中最终保留：

- 参数校验
- CLI 输出
- `start-pac` 的兼容入口处理

`conn_mgr.go` 中当前大量实现逻辑应明显瘦身。

### P1-5 Web 改为直接调用 `runtime.Service`

重点修改文件：

- [web/api.go](file:///d:/Chaos/go/v2sub/web/api.go)
- [web/service.go](file:///d:/Chaos/go/v2sub/web/service.go)

改造目标：

- `/conn/start` 直接 `runtime.Start()`
- `/conn/stop` 直接 `runtime.Stop()`
- `/conn/restart` 直接 `runtime.Restart()`
- `/conn/status` 直接 `runtime.Status()`

改造后删除以下主路径依赖：

- `v2subConnStart()` 内部再起 `v2sub -conn start`
- `v2subConnKill()` 内部再起 `v2sub -conn kill`
- `runFlag` 主状态职责
- `lastStartTimeUnix` 主状态职责

### P1-6 统一 Web 返回结构

当前 Web conn 相关接口有明显“动作状态”和“真实状态”混用问题。

P1 建议统一为：

```json
{
  "code": "1000",
  "msg": "ok",
  "data": {
    "running": true,
    "pid": 1234,
    "startedAtUnix": 1710000000,
    "binaryPath": "/usr/local/bin/v2ray",
    "configPath": "/etc/v2sub/config.json",
    "message": "running"
  }
}
```

这样前端只需要处理一个稳定结构。

### P1-7 清理 `web/service.go` 的二进制套壳逻辑

P1 完成后，`web/service.go` 应只保留真正需要的通用封装。

连接管理相关逻辑原则上应移除：

- 执行 `v2sub -conn ...`
- 拼接 shell 命令
- 依赖 `command.RunSyncForResultCb` 跟踪连接状态

如果某些 `sub/ser/conf` API 暂时仍通过执行二进制复用 CLI，可以后续继续收敛；但 `conn` 这条链要优先收口。

### P1-8 统一错误处理

P1 建议逐步把 `os.Exit` 风格从 runtime 主路径剥离。

目标：

- runtime 返回 `error`
- CLI 决定如何打印/退出
- Web 决定如何转为 HTTP JSON

这样可以避免内部 service 因 `os.Exit` 直接杀死 Web 进程。

### P1-9 P1 验证任务

必须验证：

1. CLI start/stop/status/restart 全部正常
2. Web start/stop/status/restart 全部直接走内部 service
3. 停掉 Web 进程不会错误影响已运行的 v2ray 状态判断
4. 真实状态与 pid 文件保持一致
5. Web 不再依赖 `runFlag` 作为主状态源
6. `conn` 模块代码规模明显收缩

## 4.4 P1 推荐改造顺序

1. 新建 `runtime/` 包并迁移状态结构
2. 迁移进程控制逻辑
3. 实现 `runtime.Service`
4. 让 `conn` 接入 `runtime.Service`
5. 再让 Web 接入 `runtime.Service`
6. 删除 Web 的二进制套壳逻辑
7. 统一 JSON 返回结构
8. 回归测试 CLI + Web

原因：

- 先稳定 CLI，再切 Web
- Web 接入时可直接复用已经验证过的 service

## 4.5 P1 风险与处理

### 风险 1：内部 service 与 CLI 输出耦合

当前很多逻辑默认面向终端输出。

P1 处理：

- runtime 只返回状态与 error
- 输出留给 CLI/Web 各自处理

### 风险 2：Web 日志行为变化

原来 `runLog` 记录的是外部命令输出；改成内部 service 后这套日志来源会变化。

P1 处理：

- 先接受 conn log 能力弱化
- 真正的运行日志后续可从 v2ray 独立日志文件补齐

### 风险 3：`start-pac` 入口与 runtime 的边界不清

P1 处理：

- 继续保留 `start-pac` 在 `conn` 层做兼容编排
- 不把 PAC 服务强行塞进 runtime service
- PAC 独立化放到 P2

## 7. 最终建议

如果按收益/风险排序，我建议实际执行时遵循下面节奏：

1. 先做 P0 的状态与 pid 管理
2. 再补 CLI `status/restart`
3. 再把 Web `status` 切到真实状态
4. 再进入 P1，抽 runtime service
5. 最后把 Web start/stop/restart 完全改成内部直调

这样可以先解决“现在最痛”的问题，再做架构收口。

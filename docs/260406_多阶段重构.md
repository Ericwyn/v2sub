# v2sub 多阶段重构方案

## 1. 背景

当前项目在订阅管理、节点选择、配置生成上已经具备基本能力，但在 `v2sub -conn start` 这一层的设计上存在明显问题，尤其是 `v2sub` 与 `v2ray` 的进程管理关系不够清晰，导致实际运行体验比较别扭。

典型现象：

- `v2sub -conn start` 启动后，`v2sub` 更像一个阻塞式启动器，而不是稳定的进程管理器
- kill 掉 `v2sub` 后，`v2ray` 可能仍然继续运行
- Web API 层通过再次调用 `v2sub` 二进制来控制连接，链路过长，状态不一致
- 当前运行状态主要依赖内存变量，而不是系统中的真实进程状态

因此，本次重构的目标不是单纯优化代码风格，而是重新梳理职责边界，让连接管理能力更稳定、更可维护。

---

## 2. 当前问题分析

### 2.1 `conn` 模块职责混杂

当前 [conn/conn_mgr.go](file:///d:/Chaos/go/v2sub/conn/conn_mgr.go) 同时承担了多种职责：

- CLI 参数解析
- 选择当前节点并生成 v2ray 配置
- 启动 v2ray
- 停止 v2ray / v2sub
- 提供 PAC 相关逻辑
- 判断 v2ray 新旧版本命令差异

这些职责放在一个模块中，导致后续很难抽离出真正稳定的“运行时管理能力”。

### 2.2 `v2sub -conn start` 是阻塞式启动器，不是可靠管理器

当前 `startV2ray()` 会直接同步执行 `v2ray`，意味着：

- `v2ray` 不退出，`v2sub` 就会一直阻塞
- `v2sub` 本身并没有把 `v2ray` 管理为一个可追踪、可恢复、可查询的独立运行对象
- 进程生命周期缺乏显式记录

这就造成了“启动了，但不好管”的问题。

### 2.3 终止逻辑依赖 `ps + grep + kill`

当前停止逻辑基于进程名扫描：

- 先执行 `ps`
- 再通过 `grep` 模糊匹配
- 手工筛选 `v2sub` / `v2ray`
- 最后 `kill pid`

这种方式的问题：

- 对 Linux 命令输出格式强依赖
- 容易误杀或漏杀
- 没有 pid 文件
- 没有进程组控制
- 没有 stale pid 清理机制
- 不方便做真实状态查询

### 2.4 Web 层通过执行二进制调用自己

当前 [web/service.go](file:///d:/Chaos/go/v2sub/web/service.go) 不是直接调用内部连接管理能力，而是再次执行 `v2sub -conn start`、`v2sub -conn kill`。

这会带来几个问题：

- Web 与 CLI 没有真正共用内部 service
- 多了一层子进程，日志和错误处理变复杂
- `runFlag` 只能表示 Web goroutine 状态，不能表示系统中真实的 v2ray 状态
- API 返回状态与真实进程状态可能不一致

### 2.5 缺少统一的运行时状态源

当前状态主要依赖：

- `runFlag`
- `lastStartTimeUnix`

这不是系统真相。真正应该以如下信息作为状态依据：

- v2ray pid
- pid 是否仍存活
- 启动时间
- 当前使用的配置文件
- 当前二进制路径
- 最近一次错误或退出信息

## 3. 重构目标

本次重构建议围绕以下三个核心目标展开。

### 3.1 配置管理与进程管理解耦

让 `sub / server / conf` 继续负责：

- 订阅管理
- 节点管理
- 配置生成

而把“启动、停止、状态查询、运行信息记录”集中交给独立运行时层处理。

### 3.2 CLI 与 Web 共享同一套连接管理能力

未来应避免：

- Web 通过 shell 再执行一层 `v2sub`

应调整为：

- CLI 解析参数后调用内部 service
- Web API 直接调用同一个 service

### 3.3 以真实运行状态替代内存假状态

需要引入：

- pid 文件
- runtime 状态文件
- 实际存活检测
- 统一 status 查询接口

让 `status` 成为可依赖的真实结果。

---

## 4. 推荐的目标架构

建议将项目职责拆成如下几层：

```text
conf/      配置读取、保存、模板生成
sub/       订阅管理
server/    节点管理、测速、默认节点设置
conn/      CLI 参数入口，仅做参数分发
runtime/   v2ray 进程启动、停止、状态管理
web/       HTTP API，直接调用内部 service
utils/     通用工具能力
```

其中，`runtime/` 是本次重构的重点。

---

## 5. 运行时层设计建议

### 5.1 抽象统一 service

建议新增统一接口，例如：

```go
type V2rayService interface {
    Start() error
    Stop() error
    Restart() error
    Status() V2rayStatus
}
```

状态结构例如：

```go
type V2rayStatus struct {
    Running       bool
    Pid           int
    StartedAtUnix int64
    BinaryPath    string
    ConfigPath    string
    Message       string
}
```

这样 CLI 和 Web 都可以调用同一个 service，而不是各自做一套。

### 5.2 引入 pid 文件与 runtime 文件

建议记录运行时元信息，例如：

- `/var/run/v2sub/v2ray.pid`
- `/var/run/v2sub/runtime.json`

如果希望兼容当前项目已有目录风格，也可以暂时先落在 `/etc/v2sub/` 下，但长期建议将运行态数据和配置数据分离。

建议 runtime 文件中至少记录：

- pid
- 启动时间
- v2ray binary path
- config path
- 最近一次启动方式
- 最近一次错误

### 5.3 Start 流程重构

推荐的启动流程：

1. 检查 v2ray binary 是否存在
2. 根据当前默认节点刷新并输出最新 config
3. 检查 pid 文件对应进程是否已存在
4. 若已有旧进程，先决定拒绝启动或自动重启
5. 后台启动 v2ray
6. 记录 pid 与 runtime 元信息
7. 返回启动结果

重点是：

- 启动应从阻塞式改为可管理的后台进程模式
- 状态应可追踪
- 启动结果应有明确记录

### 5.4 Stop 流程重构

推荐停止流程：

1. 读取 pid 文件
2. 校验 pid 是否仍有效
3. 优先发送温和终止信号
4. 等待短时间退出
5. 若未退出，再强制 kill
6. 清理 pid 文件与 runtime 文件
7. 返回停止结果

这样可以彻底替代 `ps + grep + kill` 的脆弱逻辑。

### 5.5 Status 流程重构

推荐状态查询流程：

1. 读取 pid 文件
2. 判断 pid 是否存活
3. 若 pid 文件存在但进程已不存在，则清理 stale pid
4. 结合 runtime 文件返回结构化状态

这样 Web 层和 CLI 层都能得到真实状态，而不是依赖内存变量。

## 6. CLI 层改造建议

目标是保持用户使用习惯不变，但内部实现切换到新 service。

建议保留原有命令形式：

- `v2sub -conn start`
- `v2sub -conn kill`
- `v2sub -conn restart`
- `v2sub -conn status`

但 `conn.ParseArgs()` 内部改为：

- 仅解析参数
- 调用 runtime service
- 将结果输出给终端

这样既兼容旧命令，又能让 conn 模块从“业务实现层”退化为“CLI 分发层”。

---

## 7. Web 层改造建议

这是最值得尽快处理的一块。

### 当前问题

[web/service.go](file:///d:/Chaos/go/v2sub/web/service.go) 通过执行 `v2sub` 二进制来控制 v2ray，这会导致：

- 多一层进程嵌套
- 状态割裂
- 日志链路复杂
- 错误定位困难

### 建议改造方向

- Web API 直接调用 runtime service
- 移除或极度瘦身 `web/service.go`
- 取消 `runFlag` 作为主状态源
- `apiConnStatus` 返回真实运行状态

重构后调用链应变为：

```text
HTTP API -> runtime service -> v2ray process
```

而不是：

```text
HTTP API -> 执行 v2sub 二进制 -> conn -> v2ray process
```

---

## 8. PAC 能力处理建议

当前 `start-pac` 把 PAC 服务和 v2ray 启动绑定在一起，设计上耦合度较高。

建议处理方式：

### 方案 A：PAC 完全独立

- `-conn start` 只负责 v2ray
- `-pac serve` 专门负责 PAC 文件服务

### 方案 B：统一走 Web

由于 Web 已经提供 `/pac.js` 能力，因此也可以考虑：

- 弱化或废弃 CLI 侧 `start-pac`
- PAC 服务统一由 Web 提供

如果只保留一套 PAC 服务入口，系统会更简单。

---

## 9. `utils/command` 的配套重构建议

当前 [utils/command/run.go](file:///d:/Chaos/go/v2sub/utils/command/run.go) 更偏向“执行命令并获取输出”，但不适合做严肃的进程管理。

建议新增更底层、面向运行时的能力，例如：

```go
func StartProcess(name string, args ...string) (*exec.Cmd, error)
func IsProcessAlive(pid int) bool
func TerminateProcess(pid int) error
func KillProcess(pid int) error
```

这样 runtime 层就可以基于明确能力实现，而不是继续堆 shell 命令。

此外，`RunResult()` 当前强依赖 `/bin/bash -c`，也说明项目整体更偏脚本式执行。后续如果继续收敛平台依赖，建议逐步把关键路径从 shell 字符串拼接改成明确参数调用。

## 10. 多阶段重构计划

为了降低风险，建议分三阶段推进。

### 第一阶段：先把进程真正管住

这是最小改动、收益最高的一阶段。

目标：

- 保持 CLI 命令格式基本不变
- 引入 pid 文件
- 引入真实状态查询
- 停止依赖 `ps + grep + kill`

具体内容：

1. 新增 pid 文件读写
2. `-conn start` 改为后台启动并记录 pid
3. `-conn kill` 优先按 pid 停止进程
4. 新增或完善 `-conn status`
5. Web 状态接口改为真实查询
6. 修复 `start` 流程中的文案与状态语义问题

阶段收益：

- 基本解决“kill 掉 v2sub 后 v2ray 还在”的问题
- 让状态变得可追踪
- 为后续 service 化打基础

### 第二阶段：统一 CLI 与 Web 的调用链

目标：

- 抽离 runtime service
- CLI 和 Web 共用同一套实现
- 去掉 Web 对 `v2sub` 二进制的依赖

具体内容：

1. 抽出 runtime service
2. CLI 改为调用 runtime service
3. Web 改为调用 runtime service
4. 删除 `web/service.go` 中对二进制执行的核心依赖
5. 统一错误、日志、状态结构

阶段收益：

- 架构清晰度明显提高
- Web 与 CLI 逻辑不再分叉
- 日志与错误更容易定位

### 第三阶段：面向长期运行环境优化

目标：

- 让项目更符合 Linux 服务化运行习惯
- 视需要引入 systemd 模式

可选内容：

1. 增加 `gen-config` 风格能力，只生成配置不启动
2. 支持由 systemd/supervisor 托管 v2ray
3. CLI 更多承担配置管理与状态查询职责
4. 进一步减少 shell 依赖
5. 对 PAC 服务进行独立化整理

阶段收益：

- 更适合生产环境
- 系统托管能力更强
- 后续维护成本更低

---

## 11. 推荐落地方向

如果优先考虑当前项目演进成本，我建议：

### 短期优先方案

先做第一阶段，再做第二阶段。

也就是先解决：

- pid 管理
- 状态真实性
- 停止逻辑可靠性

之后再做：

- runtime service 抽离
- Web 去二进制依赖

这是风险最小、收益最明确的路径。

### 长期理想方案

如果项目继续长期维护，最终形态建议是：

- `v2sub` 负责配置、订阅、节点与状态信息
- `v2ray` 的生命周期交给 systemd 或 supervisor 托管
- Web 只调用内部 service，不再执行二进制

即：

- 配置管理归 `v2sub`
- 进程托管归系统服务

这是最符合 Linux 生态习惯的模式。

---

## 12. 建议的实施优先级

### P0

- 引入 pid 文件
- 引入真实 status
- 替换 `ps + grep + kill`
- 修正当前 `-conn start`/`kill` 语义

### P1

- 抽离 runtime service
- Web 直接调用内部 service
- 删除 `runFlag` 的主状态职责
- 统一状态结构与错误输出

### P2

- PAC 独立化
- `utils/command` 能力下沉
- 支持 systemd 模式
- 降低 shell 依赖

---

## 13. 一句话总结

本次重构的核心，不是简单重写 `conn_mgr.go`，而是把项目从“脚本式启动工具”逐步演进为“配置管理 + 运行时管理分离”的结构。

先用 pid 与真实状态把连接管理做稳，再把 Web 与 CLI 统一到同一个内部 service，最后再考虑 systemd 化，是一条最稳妥的落地路径。
